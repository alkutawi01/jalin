## S7 lejar entitlement dan peraturan langganan (97%; kes tarikh saya semak betul)
- NOTA SAYA: kod hanya ada ID pada h2 dan nota kaki, TIADA ID blok stabil: prasyarat sambung bacaan merentas peranti (calon: ID h2 + indeks perenggan + cap jari teks pendek).
- Peraturan tarikh tunggal: Gregorian, Asia/Kuala_Lumpur, simpan timestamptz UTC, kekal waktu tempatan; hari sasaran tiada = hari terakhir bulan; selang [starts_at, ends_at) tamat eksklusif (bukan 23:59:59). Kes: 31 Jan 2027 10:00 +1b = 28 Feb 2027 10:00; 29 Feb 2024 15:30 +12b = 28 Feb 2025 15:30; 30 Ogos 2026 08:00 +6b = 28 Feb 2027 08:00; 30 Ogos 2027 +6b = 29 Feb 2028; 8 Okt 2026 20:00 +12b = 8 Okt 2027 20:00. Paparan: "Akses sehingga 28 Februari 2027, 10:00 pagi (MYT)". Penambahan berperingkat beza: 31 Jan +1b +1b = 28 Mac (dokumenkan).
- Penindanan: start = max(now, effective_end) untuk skop sama; skop berlainan garis masa berasingan; had 24 bulan baki akses pada masa tebus (semak tarikh tamat vs now+24 bulan), kod ditolak kekal boleh ditebus; serentak dikunci satu demi satu.
- Peristiwa lejar: GRANT (pautan unik ke redemption), ADMIN_GRANT (sebab+admin), REVOKE (sasar grant tertentu), ADJUST_POSITIVE (peruntukan baru), ADJUST_NEGATIVE (interval pembatalan eksplisit), REFUND_RECORDED (+REVOKE jika berkaitan; pulangan tak semestinya batal hak), TRANSFER_OUT+IN (atomik). Kebenaran berperingkat: sokongan siasat sahaja; langganan beri/laras dalam had; batal dan pindah kebenaran lebih tinggi + audit. KRITIKAL: Grant A (Jan-Feb), B (Feb-Mac); batal A, B KEKAL Feb-Mac (tiada pemajuan senyap); jurang dibetulkan admin dengan peristiwa baharu. Unjuran = gabungan interval grant sah.
- rebuildEntitlements(readerId, scope): baca ikut sequence_id stabil, bina interval, guna batal/laras, gabung, hasilkan unjuran dan baki. Ujian: jalan 100 kali sama; unjuran produksi == bina semula; batal grant pertama/tengah/terakhir; dua tebus serentak; rollback. SELECT ... FOR UPDATE pada baris kunci (reader_id, scope) dalam transaksi yang juga kunci kod tebus; urutan kunci konsisten (elak deadlock).
- Status BM: aktif ("Langganan anda aktif sehingga [tarikh dan waktu]."), hampir tamat <=7 hari, tamat, ditangguh, dibatalkan. Tiada grace V1; tamat = akses premium tutup pada permintaan pelayan berikutnya (halaman sedia ada dalam pelayar tak boleh ditarik balik). Akses awal yang sudah jadi percuma kekal boleh dibaca.
- V1: tiada percubaan percuma automatik; promosi manual guna ADMIN_GRANT (had kuantiti+audit); kod promosi tanpa kad kemudian guna enjin sama.
- Keputusan Izzat: waktu tepat atau hari penuh?; had timbunan 24 bulan?; tiada grace?; batal tak ubah grant berikutnya?; siapa batal/pindah/laras?; semua produk satu skop Jalin Plus V1?

## S8 kod tebus dan keselamatan penjanaan (97%; matematik entropi saya semak betul)
- Format: 12 aksara rawak Crockford base32 (abjad 0123456789ABCDEFGHJKMNPQRSTVWXYZ) + 1 aksara semak = 13 aksara, paparan 7KQF-2M9X-HD4R-C (sengkang untuk bacaan sahaja). CSPRNG. NOTA SAYA: ChatGPT cadang checksum "Crockford mod 37" yang guna simbol tambahan (*~$=U) di luar abjad 32; saya akan pilih aksara semak ringkas daripada abjad 32 itu sendiri (cth jumlah berpemberat mod 32) dengan ujian sendiri, dan menetapkannya sebagai satu algoritma tunggal, bukan campuran.
- Risiko tekaan = N x percubaan / 2^60. Dengan 1,000 percubaan: N=1,000 -> 8.67e-13 (80 bit: 8.27e-19); N=100,000 -> 8.67e-11 (80 bit: 8.27e-17). 60 bit cukup bersyarat untuk 1,000 kad; untuk 100,000 kad diterima jika had kadar global ketat, pantauan dan pengaktifan selepas jualan; margin lebih besar = 16 aksara (80 bit). Produk TIDAK dalam bahagian rawak (jenis paparan di kad + metadata batch; sahkan di pelayan).
- Penjanaan: CSPRNG, penapis kata tidak sopan (uji bias), pertindihan lewat UNIQUE(key_id, code_mac), simpan semua MAC dalam satu transaksi dan semak jumlah. Kod bersih dihantar SEKALI melalui HTTPS ke pelayar admin untuk jana PDF setempat (tiada simpan pelayan). Risiko Vercel: respons terputus selepas commit = kod hilang: jangan jana semula daripada seed; guna status PENDING_PRINT > PRINT_CONFIRMED atau VOIDED; batch kecil dahulu (50-100 kad); batch hilang artefak = batal keseluruhan. Kod bukan dalam log, URL API, pemantauan atau storan pelayar berterusan. Simpanan PDF oleh admin ialah tanggungjawab operasi (prosedur musnah).
- HMAC-SHA-256 dengan input berkonteks "jalin-redeem-v1:<kod>", kunci >=256 bit dalam pengurusan rahsia persekitaran (bukan Postgres), key_id; putaran: kod baharu kunci baharu, kod lama disahkan dengan kunci lama; kunci bocor: henti pengeluaran, nilai, batal kod berisiko, ganti kad; kunci hilang: kod lama tak boleh dicari, perlu pulih rahsia daripada sandaran selamat atau ganti batch; simpan kunci lama terlindung selagi kod sah.
- Input: terima huruf kecil/ruang/sengkang; O->0, I/L->1; semak panjang+checksum sebelum DB TETAPI SEMUA percubaan (termasuk checksum salah) tertakluk had kadar. Awal: 5/akaun/15 min, 20/IP/jam, had global, perlindungan IP berkongsi (sekolah/pejabat). Mesej umum: "Kod tidak dapat disahkan. Semak kod atau hubungi sokongan Jalin." tanpa dedah status.
- QR: HANYA https://jalin.adjung.com/tebus (TANPA kod). Pembeli imbas, log masuk, taip kod bercetak, lihat ringkasan produk, tekan "Sahkan Penebusan". Imbas sahaja tidak guna kod. Autofill fragmen = penilaian ancaman berasingan nanti.
- Cetak semula: V1 batal + jana baharu (bukan artefak dienkripsi); kod yang sudah diaktifkan tak boleh dicetak semula tanpa prosedur penggantian rasmi.
- Ujian: 100,000 kod tanpa pertindihan tak terkawal; taburan+penapis; variasi input; checksum salah guna kuota; dua tebus serentak; respons cetak terputus; putaran kunci; kunci hilang/bocor; QR tak tebus dan tiada kod dalam log/URL; cetakan sebenar 3 telefon + pencetak pilihan.
- Keputusan Izzat: 60 atau 80 bit; sahkan QR tanpa kod; polisi batal+jana semula; kuantiti maksimum batch V1; siapa boleh aktif/batal batch.

## S9 aliran penebusan, penyalahgunaan, konkurensi (98%)
- Checksum: ChatGPT akui jumlah berpemberat mod 32 lemah (pertukaran bersebelahan tak dikesan); cadang Damm/Verhoeff disesuaikan untuk 32 aksara. NOTA SAYA: kebolehlaksanaan Damm pada tertib 32 (kuasa 2) TIDAK saya sahkan; keputusan pelaksanaan = pilih algoritma yang dibuktikan dengan ujian lengkap (semua kesilapan satu aksara dan semua pertukaran bersebelahan), contoh calon mod-31 berpemberat dalam abjad (pengecualian pasangan 0/Z perlu diperiksa) atau jadual Damm tertib 32 yang disahkan. Checksum = pengesan taip, bukan kawalan keselamatan.
- Mesin keadaan kod: generated > pending_print > print_confirmed > issued (diaktifkan = BOLEH ditebus, bukan semestinya dijual; untuk "aktif selepas jualan" perlu rekod pengesahan jualan pengedar); pending_print/print_confirmed > voided; issued > revoked; issued > redeemed (lewat redemptions). Haram: voided/revoked > issued, redeemed > issued, generated > redeemed. Pembatalan selepas tebus = REVOKE entitlement, bukan ubah kod.
- Titik akhir: POST /api/tebus, GET /api/me/entitlement, GET /api/me/redemptions, admin berasingan. Emel selepas tebus = transactional outbox: email_outbox(id, event_id UNIQUE, template, recipient, payload_minimal, status, attempts, next_attempt_at, sent_at, last_error); tulis bersama entitlement dalam transaksi; pekerja tuntut dengan FOR UPDATE SKIP LOCKED/pajakan; cuba semula 1, 5, 30 minit kemudian tanda semakan; sekurang-kurangnya sekali (bukan tepat sekali), guna kunci idempotensi penyedia; tiada OTP bersih dalam outbox. Jika hanya cron harian: hantar segera + butang "Cuba Hantar Semula". Neon pg_cron ditangguh. Fail Blob BUKAN storan kod bersih.
- Neon: pooled connection/pemacu serverless yang menyokong transaksi Kysely (BEGIN, kunci baris, COMMIT dalam konteks sama). Indeks wajib: reader_sessions(token_hash) unik; redeem_codes(key_id, code_mac) unik; redemptions(code_id) unik; entitlement_periods(reader_id, scope, ends_at); email_outbox(status, next_attempt_at). Bab percuma tiada pertanyaan entitlement. Sasaran p95 hipotesis: 500 pembaca (2,500 halaman/hari) <800ms; 5,000 (25,000/hari) <1,200ms. Ujian k6 pada staging 10/25/50 serentak; ukur p95, ralat, sambungan DB, masa tunggu kunci. Compute Neon boleh tidur: permintaan pertama lebih perlahan.
- Sandaran: sahkan PITR dan tetingkap pelan SEBENAR. RPO 24j / RTO 4j untuk editorial; untuk tebus berbayar RPO hampir sifar belum boleh dijamin. BAHAYA PEMULIHAN: restore DB ke masa lalu boleh hilangkan rekod tebus sedangkan kad fizikal ada: kod boleh ditebus dua kali. Sebelum buka semula tebus selepas restore: bandingkan rekod transaksi, audit, sandaran bebas; bekukan tebus jika integriti tak terbukti. Kunci HMAC dalam pengurus kata laluan ber-MFA + salinan luar talian (bukan repositori, bukan bersama sandaran DB). Neon gagal: laman yang ada boleh dibaca tetapi jangan janji semua dinamik; emel gagal: tangguh log masuk baharu, sesi sedia ada diteruskan.
- Semakan harian automatik: cron terakhir selesai; outbox tertunda; redemption tanpa grant; unjuran == bina semula; batch siap jumlah tepat; kod batal tak ditebus selepas batal; lonjakan gagal OTP/tebus. Satu emel ringkasan jika masalah; jika penyedia emel gagal tunjuk status merah dalam admin + semakan manual. Suis hentikan tebus disimpan di DB/semak di pelayan (bukan env var) tanpa deploy.
- Staging: Neon branch/pangkalan data berasingan, HMAC berlainan, domain ujian, emel sandbox; jangan salin emel pembaca sebenar. Feature flag (tiada rahsia dalam jadual konfigurasi). Migrasi sekali lewat pipeline. Batch perubahan dalam PR untuk elak had deploy.
- Kos bulanan simulasi (formula, bukan sebut harga): emel RM0-50; Neon RM0-100; Vercel RM0-120; domain RM3-10; cetakan RM0-200; sokongan RM0-300 => ~RM3-780/bulan, tidak termasuk penghasilan karya/pembangunan/cukai; rekod nilai masa Izzat.
- Keputusan Izzat: sahkan pelan Vercel/Neon sebenar; bajet bulanan maksimum; penyedia emel; tempat simpan rahsia pemulihan; siapa terima amaran; tempoh gangguan boleh diterima. Syarat: JANGAN lancar kad berbayar sebelum ujian pemulihan DB buktikan kod yang sudah ditebus tak boleh dapat grant kedua selepas restore.
